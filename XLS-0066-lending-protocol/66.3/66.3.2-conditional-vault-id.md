# 66.3.2 Conditional LoanBroker VaultID

## 1. Abstract

Under `LendingProtocolV1_2`, `LoanBrokerSet` carries exactly one of `VaultID` and `LoanBrokerID`. `VaultID` is required when the transaction creates a `LoanBroker` and must be absent when it modifies one. A modification resolves the Vault from the stored `LoanBroker.VaultID`.

## 2. Motivation

`LoanBrokerSet` creates a `LoanBroker` when `LoanBrokerID` is absent and modifies one when it is present. The parent specification requires `VaultID` in both cases, but the Vault association is fixed when the `LoanBroker` is created and cannot change. On modification the field only repeats a value already stored on the ledger, and a mismatch fails with `tecNO_PERMISSION` after the transaction fee is charged.

## 3. Specification

This patch changes the parent [XLS-66](../README.md) sections named below. All other parent behavior is unchanged.

### 3.1 Transaction: `LoanBrokerSet`

#### 3.1.1 Fields

Amend parent [§3.3.1](../README.md#331-fields) as follows:

| Field Name     |  Required   | JSON Type | Internal Type | Default Value | Description                                                                                                           |
| -------------- | :---------: | :-------: | :-----------: | :-----------: | :-------------------------------------------------------------------------------------------------------------------- |
| `VaultID`      | Conditional | `string`  |   `HASH256`   |     `N/A`     | The Vault ID that the Lending Protocol will use to access liquidity. Required on creation; forbidden on modification. |
| `LoanBrokerID` | Conditional | `string`  |   `HASH256`   |     `N/A`     | The Loan Broker ID that the transaction is modifying. Absent on creation; present on modification.                    |

Exactly one of `VaultID` and `LoanBrokerID` must be present:

- If `LoanBrokerID` is absent, the transaction creates a `LoanBroker`. `VaultID` is required and identifies the Vault that backs the new `LoanBroker`. It is stored in `LoanBroker.VaultID`.
- If `LoanBrokerID` is present, the transaction modifies an existing `LoanBroker`. `VaultID` must be absent. The Vault is `Vault(LoanBroker(LoanBrokerID).VaultID)`.

Before `LendingProtocolV1_2`, `VaultID` is required in both cases, as in the parent specification.

#### 3.1.2 Failure Conditions

##### 3.1.2.1 Data Verification

Amend parent [§3.3.3.1](../README.md#3331-data-verification) check 1:

1. - `LendingProtocol (parent)`: `VaultID` is zero. (`temINVALID`)
   - `LendingProtocolV1_2`: `VaultID` is present and is zero. (`temINVALID`)

Append to parent [§3.3.3.1](../README.md#3331-data-verification):

10. - `LendingProtocol (parent)`: The check does not apply.
    - `LendingProtocolV1_2`: `LoanBrokerID` is not specified and `VaultID` is absent. (`temINVALID`)
11. - `LendingProtocol (parent)`: The check does not apply.
    - `LendingProtocolV1_2`: `LoanBrokerID` is specified and `VaultID` is present. (`temINVALID`)

##### 3.1.2.2 Protocol-Level Failures

Amend parent [§3.3.3.2](../README.md#3332-protocol-level-failures) as follows:

- Parent check 9 (the transaction `VaultID` does not match `LoanBroker(LoanBrokerID).VaultID`):
  - `LendingProtocol (parent)`: The check applies unchanged. (`tecNO_PERMISSION`)
  - `LendingProtocolV1_2`: The check does not apply, because Data Verification check 11 rejects any modification that carries `VaultID`.
- Parent check 11 (precision validation) uses the Vault that backs the `LoanBroker`:
  - Creation: `Vault(VaultID).Asset`.
  - Modification under `LendingProtocolV1_2`: `Vault(LoanBroker(LoanBrokerID).VaultID).Asset`.

All other parent checks keep their numbers and conditions.

#### 3.1.3 State Changes

Unchanged. Creation uses `Vault(VaultID)` as in the parent. Modification does not change `LoanBroker.VaultID`.

Modifying an existing `LoanBroker` under `LendingProtocolV1_2`:

## 4. Rationale

The Vault association of a `LoanBroker` is immutable, so a modification has no use for `VaultID`. Requiring the field adds a value that clients must look up and repeat, and gives them a way to get it wrong.

Rejecting a modification that carries `VaultID`, rather than accepting a matching value, keeps one form for each case. "Exactly one of `VaultID` and `LoanBrokerID`" decides from the transaction alone whether it creates or modifies a `LoanBroker`, so the checks run in preflight and need no ledger state.

## 5. Backwards Compatibility

After `LendingProtocolV1_2` is enabled, a `LoanBrokerSet` that modifies a `LoanBroker` and includes `VaultID` fails with `temINVALID`, even if the value matches `LoanBroker.VaultID`. Clients must omit `VaultID` when `LoanBrokerID` is present. Creation is unchanged.

Before the amendment, a mismatched `VaultID` on modification failed with `tecNO_PERMISSION`, which is applied to the ledger and charges the fee. After the amendment, the same transaction fails with `temINVALID`, which is not applied and charges no fee.

Before the amendment, the parent behavior applies unchanged, including the order of the existing `tecNO_ENTRY` and `tecNO_PERMISSION` checks.

## 6. Test Plan

Tests exercise `LoanBrokerSet` with the amendment both enabled and disabled for these cases:

- Creation with `VaultID`, without `VaultID`, and with a zero `VaultID`.
- Modification without `VaultID`, with a matching `VaultID`, and with a mismatched `VaultID`.

With the amendment enabled, they confirm that a modification without `VaultID` updates `Data` and `DebtMaximum` and validates precision against the stored Vault's asset. With the amendment disabled, they confirm that the parent checks and their order are unchanged.

## 7. Security Considerations

A modification cannot reassign a `LoanBroker` to another Vault in either version. Before the amendment the mismatch check prevents it; after the amendment the transaction cannot name a Vault at all. Owner checks are unchanged. Implementations must read the Vault from `LoanBroker.VaultID` on modification so that precision validation uses the asset that actually backs the `LoanBroker`.
