# 66.1.1 Loan Cash-Basis Accounting

## 1. Abstract

Under the `LendingProtocolV1_1` amendment, for a Vault with `LEVersion == 1` (cash basis, see [XLS-65.1.3](../../XLS-0065-single-asset-vault/65.1/65.1.3-vault-cash-basis.md)), `LoanBroker.DebtTotal` tracks loan principal only and `Vault.AssetsTotal` recognises interest when it is collected rather than when a Loan is issued. `LoanSet`, `LoanPay` and `LoanManage` change accordingly. For a Vault with `LEVersion` absent, the parent behaviour applies unchanged, even while the amendment is enabled.

## 2. Motivation

Under instant interest recognition, issuing a Loan immediately increases `Vault.AssetsTotal` by the expected interest and `LoanBroker.DebtTotal` by the principal plus expected interest. The `AssetsMaximum` and `DebtMaximum` caps are therefore consumed by interest that has not been paid, and the first-loss capital requirement, which is a rate applied to `DebtTotal`, is sized against expected interest as well as principal.

## 3. Specification

This patch changes the parent [XLS-66](../README.md) sections named below. It uses `Vault.LEVersion` as defined by [XLS-65.1.3](../../XLS-0065-single-asset-vault/65.1/65.1.3-vault-cash-basis.md). All other parent behavior is unchanged.

Every `LendingProtocolV1_1` branch below is gated on `Vault.LEVersion == 1`, read from the `Vault` the `LoanBroker` is attached to. For a Vault with `LEVersion` absent, the `LendingProtocol (parent)` branch applies.

### 3.1 Ledger Entry: `LoanBroker`

#### 3.1.1 Fields

Amend the `DebtTotal` description in parent [§3.1.2](../README.md#312-fields):

- `LendingProtocol (parent)`: The total asset amount the protocol owes the Vault, including interest.
- `LendingProtocolV1_1`: If `Vault.LEVersion == 1`, the total loan principal the protocol owes the Vault, excluding interest.

#### 3.1.2 Accounting

The examples in parent [§3.1.10](../README.md#3110-accounting) and [§3.1.11](../README.md#3111-first-loss-capital) describe a Vault with `LEVersion` absent: they credit expected interest at origination, and their `DefaultAmount` is principal plus interest. For a Vault with `LEVersion == 1`, `DebtTotal` captures principal only, and `DefaultAmount` is principal only. §3.5 below walks one Loan through both models.

### 3.2 Transaction: `LoanSet`

#### 3.2.1 Failure Conditions

Amend these checks in parent [§3.8.5.2](../README.md#3852-protocol-level-failures):

6. - `LendingProtocol (parent)`: `Vault.AssetsMaximum != 0` and `Vault.AssetsTotal >= Vault.AssetsMaximum` (vault at capacity). (`tecLIMIT_EXCEEDED`)
   - `LendingProtocolV1_1`: The check does not apply if `Vault.LEVersion == 1`.
7. - `LendingProtocol (parent)`: `Vault.AssetsMaximum != 0` and `Vault.AssetsTotal + InterestDue > Vault.AssetsMaximum` (expected interest would exceed vault assets cap). (`tecLIMIT_EXCEEDED`)
   - `LendingProtocolV1_1`: The check does not apply if `Vault.LEVersion == 1`.
8. - `LendingProtocol (parent)`: `LoanBroker.DebtMaximum != 0` and `LoanBroker.DebtMaximum < LoanBroker.DebtTotal + PrincipalRequested + InterestDue` (exceeds maximum debt). (`tecLIMIT_EXCEEDED`)
   - `LendingProtocolV1_1`: If `Vault.LEVersion == 1`, `LoanBroker.DebtMaximum != 0` and `LoanBroker.DebtMaximum < LoanBroker.DebtTotal + PrincipalRequested` (exceeds maximum debt). (`tecLIMIT_EXCEEDED`)
9. - `LendingProtocol (parent)`: `LoanBroker.CoverAvailable < (LoanBroker.DebtTotal + PrincipalRequested + InterestDue) × LoanBroker.CoverRateMinimum` (insufficient first-loss capital). (`tecINSUFFICIENT_FUNDS`)
   - `LendingProtocolV1_1`: If `Vault.LEVersion == 1`, `LoanBroker.CoverAvailable < (LoanBroker.DebtTotal + PrincipalRequested) × LoanBroker.CoverRateMinimum` (insufficient first-loss capital). (`tecINSUFFICIENT_FUNDS`)

Checks 6 and 14 do not apply to a cash-basis Vault because origination does not credit `InterestDue` into `Vault.AssetsTotal`. A replacement such as `Vault.AssetsTotal > Vault.AssetsMaximum` is not used: it would reject origination from a Vault that is over the cap only because of collected interest. The matching change to the Vault cap invariant is in [XLS-65.1.3](../../XLS-0065-single-asset-vault/65.1/65.1.3-vault-cash-basis.md) §3.1.4.

#### 3.2.2 State Changes

Amend steps 6 and 7 of parent [§3.8.6](../README.md#386-state-changes); all other steps are unchanged:

6. - `LendingProtocol (parent)`: Update `Vault` object:
     - Decrease `Vault.AssetsAvailable` by `PrincipalRequested`.
     - Increase `Vault.AssetsTotal` by `InterestDue` (interest owed to the Vault, excluding management fee).
   - `LendingProtocolV1_1`: If `Vault.LEVersion == 1`, update `Vault` object:
     - Decrease `Vault.AssetsAvailable` by `PrincipalRequested`.
     - `Vault.AssetsTotal` is unchanged; `InterestDue` is not recognised at origination.
7. - `LendingProtocol (parent)`: Update `LoanBroker` object:
     - Increase `LoanBroker.DebtTotal` by `PrincipalRequested + InterestDue`.
     - Increment `LoanBroker.OwnerCount` by `1`.
     - Increment `LoanBroker.LoanSequence` by `1`.
   - `LendingProtocolV1_1`: If `Vault.LEVersion == 1`, update `LoanBroker` object:
     - Increase `LoanBroker.DebtTotal` by `PrincipalRequested` only; `InterestDue` is excluded.
     - Increment `LoanBroker.OwnerCount` by `1`.
     - Increment `LoanBroker.LoanSequence` by `1`.

This patch does not change the Borrower `OwnerCount` increment or the directory links in parent steps 2 and 8.

### 3.3 Transaction: `LoanManage`

#### 3.3.1 Failure Conditions

Amend check 8 in parent [§3.10.4.2](../README.md#31042-protocol-level-failures):

8. - `LendingProtocol (parent)`: `tfLoanImpair` is specified and `Vault.LossUnrealized + (Loan.TotalValueOutstanding - Loan.ManagementFeeOutstanding) > Vault.AssetsTotal - Vault.AssetsAvailable` (impairment would exceed vault's unavailable assets). (`tecLIMIT_EXCEEDED`)
   - `LendingProtocolV1_1`: If `Vault.LEVersion == 1`, `tfLoanImpair` is specified and `Vault.LossUnrealized + Loan.PrincipalOutstanding > Vault.AssetsTotal - Vault.AssetsAvailable` (impairment would exceed vault's unavailable assets). (`tecLIMIT_EXCEEDED`)

#### 3.3.2 State Changes

Amend only the amount computations in items 1 to 3 of parent [§3.10.5](../README.md#3105-state-changes). The nested substeps (flags, transfers, `DebtTotal`, `LossUnrealized` and field clears) are unchanged, except that they use these amounts:

1. If the `tfLoanDefault` flag is specified, compute `DefaultAmount`:
   - `LendingProtocol (parent)`: `DefaultAmount = Loan.TotalValueOutstanding - Loan.ManagementFeeOutstanding` (principal + interest owed to Vault).
   - `LendingProtocolV1_1`: If `Vault.LEVersion == 1`, `DefaultAmount = Loan.PrincipalOutstanding` (principal only). `Loan.ManagementFeeOutstanding` is excluded in both branches.
2. If the `tfLoanImpair` flag is specified, compute `LossUnrealized`:
   - `LendingProtocol (parent)`: `LossUnrealized = Loan.TotalValueOutstanding - Loan.ManagementFeeOutstanding`.
   - `LendingProtocolV1_1`: If `Vault.LEVersion == 1`, `LossUnrealized = Loan.PrincipalOutstanding`.
3. If the `tfLoanUnimpair` flag is specified, compute `LossReversed`:
   - `LendingProtocol (parent)`: `LossReversed = Loan.TotalValueOutstanding - Loan.ManagementFeeOutstanding`.
   - `LendingProtocolV1_1`: If `Vault.LEVersion == 1`, `LossReversed = Loan.PrincipalOutstanding`.

`MinimumCover`, `DefaultCovered` and `VaultLoss` keep their parent formulas and use the amended `DefaultAmount` and the principal-only `LoanBroker.DebtTotal`.

### 3.4 Transaction: `LoanPay`

#### 3.4.1 State Changes

In parent [§3.11.5](../README.md#3115-state-changes), the introduction to "`LoanBroker` and `Vault` Object State Changes" applies `valueChange` to both objects. For a Vault with `LEVersion == 1`, `valueChange` is not applied to either object; steps 6 and 7 use `principalPaid` and `interestPaid` instead.

Amend steps 6 and 7; all other steps, including the `Loan` updates and the asset transfers, are unchanged:

6. **`LoanBroker` Updates**:
   - `LoanBroker.DebtTotal`:
     - `LendingProtocol (parent)`: decreased by `totalToVault - valueChange`.
     - `LendingProtocolV1_1`: If `Vault.LEVersion == 1`, decreased by `principalPaid` only; `valueChange` does not apply.
   - If fees were directed to the cover pool, `LoanBroker.CoverAvailable` increases by `totalToBroker`.
7. **`Vault` Updates**:
   - `Vault.AssetsAvailable` increases by `totalToVault`.
   - `Vault.AssetsTotal`:
     - `LendingProtocol (parent)`: adjusted by `valueChange`.
     - `LendingProtocolV1_1`: If `Vault.LEVersion == 1`, increased by `interestPaid` only; `valueChange` does not apply.

Principal repayment does not change `Vault.AssetsTotal`. Because checks 6 and 14 of §3.2.1 do not apply to a cash-basis Vault, an interest receipt may raise `Vault.AssetsTotal` above `Vault.AssetsMaximum`; the cap restricts deposits, not interest receipts.

#### 3.4.2 Appendix Formulas

The appendix statements below describe a Vault with `LEVersion` absent. For a Vault with `LEVersion == 1`, read them as follows:

- Parent Appendix A-2 [§4.2](../README.md#42-value-impact) states that late-payment `valueChange` is applied directly to `Vault.AssetsTotal` and `LoanBroker.DebtTotal`. For a cash-basis Vault it is applied to neither; `Vault.AssetsTotal` increases by `interestPaid` and `LoanBroker.DebtTotal` decreases by `principalPaid`.
- Parent Appendix [A-3.2](../README.md#a-32-payment-processing), [A-3.2.2](../README.md#a-322-late-payment) and [A-3.2.4](../README.md#a-324-early-full-repayment) state that `valueChange` is reflected in `Vault.AssetsTotal` and `LoanBroker.DebtTotal`. For a cash-basis Vault neither field is reconciled against `valueChange`.
- Parent Appendix A-2 [§8.1](../README.md#81-default-amounts) formula (34) becomes:

$$
DefaultAmount =
\begin{cases}
PrincipalOutstanding & \text{if } Vault.LEVersion = 1 \\
PrincipalOutstanding + InterestOutstanding_{net} & \text{otherwise}
\end{cases}
\quad \text{(34)}
$$

`valueChange` is still computed. It remains part of the `Loan` state transition, which this patch does not change: `LoanPay` adjusts `Loan.TotalValueOutstanding` by the re-amortization `valueChange` after an overpayment (parent §3.11.5 step 5), and `try_overpayment` rejects an overpayment with `valueChange > 0` (parent [A-3.3](../README.md#a-33-pseudo-code)). Late-payment `valueChange` is not reflected in `Loan.TotalValueOutstanding` under either model. `principalPaid`, `interestPaid` and `feePaid` are computed as in the parent.

### 3.5 Worked Example: Loan Default Under Both Models

This example walks a single Loan through `LoanSet`, `LoanPay` and `LoanManage(tfLoanDefault)`. It uses the figures from parent §3.1.10 and §3.1.11. "Legacy" is a Vault with `LEVersion` absent; "cash basis" is a Vault with `LEVersion == 1`. Both can exist on the ledger once the amendment is enabled; a legacy Vault never moves to the cash-basis column.

**Initial State (before `LoanSet`)**

Vault: `AssetsTotal = 100,000`, `AssetsAvailable = 100,000`

LoanBroker: `DebtTotal = 0`, `ManagementFeeRate = 10%`, `CoverRateMinimum = 10%`, `CoverRateLiquidation = 10%`, `CoverAvailable = 1,000`

Loan terms: `PrincipalRequested = 1,000`, gross interest over the loan's life = `100` (simplified, as in the parent examples), so management fee = `10` and net interest due to the Vault = `90`.

**Step 1: `LoanSet`**

| Field                   | Legacy                         | Cash basis                     |
| ----------------------- | ------------------------------ | ------------------------------ |
| `Vault.AssetsTotal`     | `100,000 + 90 =` **100,090**   | unchanged: **100,000**         |
| `Vault.AssetsAvailable` | `100,000 - 1,000 =` **99,000** | `100,000 - 1,000 =` **99,000** |
| `LoanBroker.DebtTotal`  | `0 + 1,000 + 90 =` **1,090**   | `0 + 1,000 =` **1,000**        |

**Step 2: `LoanPay` (one payment: principal = 500, gross interest = 50, management fee = 5, net interest = 45)**

`totalToVault = 500 + 45 = 545` in both models.

| Field                   | Legacy                                     | Cash basis                                    |
| ----------------------- | ------------------------------------------ | --------------------------------------------- |
| `Vault.AssetsTotal`     | unchanged (`valueChange = 0`): **100,090** | `100,000 + 45 =` **100,045** (`interestPaid`) |
| `Vault.AssetsAvailable` | `99,000 + 545 =` **99,545**                | `99,000 + 545 =` **99,545**                   |
| `LoanBroker.DebtTotal`  | `1,090 - 545 =` **545**                    | `1,000 - 500 =` **500** (`principalPaid`)     |

`Loan.PrincipalOutstanding = 500` in both models, because `Loan` fields are not changed by this patch. The remaining scheduled interest is `45` and the remaining management fee is `5`, so `Loan.TotalValueOutstanding = 550` and `Loan.ManagementFeeOutstanding = 5`.

**Step 3: `LoanManage(tfLoanDefault)`**

_Legacy:_

- `DefaultAmount = TotalValueOutstanding - ManagementFeeOutstanding = 550 - 5 = 545`
- `MinimumCover = DebtTotal × CoverRateMinimum = 545 × 10% = 54.5`
- `DefaultCovered = min(MinimumCover × CoverRateLiquidation, DefaultAmount, CoverAvailable) = min(5.45, 545, 1000) = 5.45`
- `VaultLoss = DefaultAmount - DefaultCovered = 545 - 5.45 = 539.55`
- `Vault.AssetsTotal = 100,090 - 539.55 =` **99,550.45**
- `Vault.AssetsAvailable = 99,545 + 5.45 =` **99,550.45**
- `LoanBroker.DebtTotal = 545 - 545 =` **0**
- `LoanBroker.CoverAvailable = 1,000 - 5.45 =` **994.55**

_Cash basis:_

- `DefaultAmount = PrincipalOutstanding = 500`
- `MinimumCover = DebtTotal × CoverRateMinimum = 500 × 10% = 50`
- `DefaultCovered = min(MinimumCover × CoverRateLiquidation, DefaultAmount, CoverAvailable) = min(5, 500, 1000) = 5`
- `VaultLoss = DefaultAmount - DefaultCovered = 500 - 5 = 495`
- `Vault.AssetsTotal = 100,045 - 495 =` **99,550**
- `Vault.AssetsAvailable = 99,545 + 5 =` **99,550**
- `LoanBroker.DebtTotal = 500 - 500 =` **0**
- `LoanBroker.CoverAvailable = 1,000 - 5 =` **995**

**Observations**

- In each model, `LoanBroker.DebtTotal` clears to `0` at default and `Vault.AssetsTotal` equals `Vault.AssetsAvailable` afterwards. The default mechanics are unchanged.
- The legacy `DefaultAmount`, `MinimumCover` and `DefaultCovered` include interest; the cash-basis figures use principal only. In this example `CoverAvailable` is not binding, so those quantities shrink with the excluded interest. That is not general: a `min` capped by `CoverAvailable` can leave the cover drawdown unchanged, and an aggregate broker `DebtTotal` can produce another ratio.
- The `0.45` difference between the two final `AssetsTotal` values is the difference in `DefaultCovered` (`5.45` against `5`). It comes from `MinimumCover` being computed on an interest-inclusive `DebtTotal` (`545`) in the legacy model and on a principal-only `DebtTotal` (`500`) under cash basis. It is a difference between the two models, not rounding within either.
- `Loan.ManagementFeeOutstanding` (`5`) is excluded from `DefaultAmount` in both models.

## 4. Rationale

Interest could have been recognised on a schedule, one payment period at a time, rather than on receipt. That was rejected because it reintroduces the original problem in a smaller form: the Vault would still credit itself with interest for a period in which the Borrower ends up not paying.

## 5. Security Considerations

Principal-only accounting makes `DebtTotal` a smaller number for the same set of Loans, so a `CoverRateMinimum` that was calibrated under instant interest recognition yields less first-loss capital. A Broker migrating to a cash-basis Vault should re-derive the rate rather than reuse it.

Both accounting models coexist on the ledger for as long as pre-amendment Vaults exist. An implementation must branch on `Vault.LEVersion` in every place it adjusts `AssetsTotal` or `DebtTotal`; branching in some places and not others corrupts the share exchange rate of the Vault.
