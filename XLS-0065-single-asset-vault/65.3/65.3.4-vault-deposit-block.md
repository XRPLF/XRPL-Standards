# 65.3.4 Vault Deposit Block

## 1. Abstract

Under `LendingProtocolV1_2`, a Vault Owner can opt in at `VaultCreate` to the ability to block and unblock deposits. The opt-in is recorded in the immutable `lsfVaultOwnerCanBlockDeposit` flag. The current state is recorded in the mutable `lsfVaultDepositBlocked` flag, which `VaultSet` toggles with `tfVaultDepositBlock` and `tfVaultDepositUnblock`. While deposits are blocked, every `VaultDeposit` fails. Withdrawals are unaffected.

## 2. Motivation

A Vault Owner may need to stop new capital from entering a Vault, for example while the Vault's strategy is being wound down or reviewed, without stopping existing depositors from redeeming. The parent specification has no way to do this short of deleting the Vault. Making the capability opt-in and immutable lets depositors see, before they deposit, whether the owner holds this power.

## 3. Specification

This patch changes the parent [XLS-65](../README.md) sections named below. All other parent behavior is unchanged.

Before `LendingProtocolV1_2` is enabled, `tfVaultOwnerCanBlockDeposit`, `tfVaultDepositBlock`, and `tfVaultDepositUnblock` are invalid transaction flags.

### 3.1 Ledger Entry: `Vault`

#### 3.1.1 Flags

Add these flags to parent [§3.1.2.1](../README.md#3121-flags):

| Flag Name                      |  Flag Value  | Modifiable? | Description                                                            |
| ------------------------------ | :----------: | :---------: | :--------------------------------------------------------------------- |
| `lsfVaultDepositBlocked`       | `0x00020000` |     Yes     | If set, deposits into the Vault are blocked.                           |
| `lsfVaultOwnerCanBlockDeposit` | `0x00040000` |     No      | If set, the Vault Owner can block and unblock deposits after creation. |

`lsfVaultDepositBlocked` is set only on a Vault that has `lsfVaultOwnerCanBlockDeposit`.

#### 3.1.2 Invariants

`lsfVaultOwnerCanBlockDeposit` is immutable: only `VaultCreate` sets it, and no transaction sets or clears it on an existing Vault. Parent [§3.1.10](../README.md#3110-invariants) invariant 14 covers Vault fields, not flags, and this patch does not add a ledger invariant check for this flag. Immutability follows from the transaction rules in §3.2 and §3.3.

### 3.2 Transaction: `VaultCreate`

#### 3.2.1 Flags

Add this flag to parent [§3.2.2](../README.md#322-flags):

| Flag Name                     |  Flag Value  | Description                                                                                                    |
| ----------------------------- | :----------: | :------------------------------------------------------------------------------------------------------------- |
| `tfVaultOwnerCanBlockDeposit` | `0x00040000` | Allows the Vault Owner to block and unblock deposits after creation. It can only be set during Vault creation. |

#### 3.2.2 Failure Conditions

Append to parent [§3.2.5.1](../README.md#3251-data-verification):

6. - `SingleAssetVault`: `tfVaultOwnerCanBlockDeposit` is set. (`temINVALID_FLAG`)
   - `LendingProtocolV1_2`: The check does not apply.

#### 3.2.3 State Changes

Extend parent [§3.2.6](../README.md#326-state-changes) step 1:

- `LendingProtocolV1_2`: If `tfVaultOwnerCanBlockDeposit` is set, set `lsfVaultOwnerCanBlockDeposit` on the new `Vault`. `lsfVaultDepositBlocked` is never set at creation.

### 3.3 Transaction: `VaultSet`

#### 3.3.1 Fields

Add this row to parent [§3.3.1](../README.md#331-fields):

| Field Name | Required | JSON Type | Internal Type | Default Value | Description                                                                                |
| ---------- | :------: | :-------: | :-----------: | :-----------: | :----------------------------------------------------------------------------------------- |
| `Flags`    |    No    | `number`  |   `UINT32`    |       0       | The standard transaction flags field. It may include the deposit-blocking flags in §3.3.2. |

#### 3.3.2 Flags

The parent `VaultSet` has no transaction-specific flags. Add:

| Flag Name               |  Flag Value  | Description                      |
| ----------------------- | :----------: | :------------------------------- |
| `tfVaultDepositBlock`   | `0x00010000` | Block deposits into the Vault.   |
| `tfVaultDepositUnblock` | `0x00020000` | Unblock deposits into the Vault. |

#### 3.3.3 Failure Conditions

Amend parent [§3.3.2.1](../README.md#3321-data-verification) check 4, and append checks 5 and 6:

4. - `SingleAssetVault`: None of the `Data`, `AssetsMaximum`, or `DomainID` fields are provided (nothing to update). (`temMALFORMED`)
   - `LendingProtocolV1_2`: None of the `Data`, `AssetsMaximum`, or `DomainID` fields are provided, and neither `tfVaultDepositBlock` nor `tfVaultDepositUnblock` is set in `Flags` (nothing to update). (`temMALFORMED`)
5. - `SingleAssetVault`: `tfVaultDepositBlock` or `tfVaultDepositUnblock` is set. (`temINVALID_FLAG`)
   - `LendingProtocolV1_2`: The check does not apply.
6. `LendingProtocolV1_2`: Both `tfVaultDepositBlock` and `tfVaultDepositUnblock` are set. (`temINVALID_FLAG`)

Append to parent [§3.3.2.2](../README.md#3322-protocol-level-failures):

7. `LendingProtocolV1_2`: `tfVaultDepositBlock` or `tfVaultDepositUnblock` is set, and the Vault does not have `lsfVaultOwnerCanBlockDeposit`. (`tecNO_PERMISSION`)
8. `LendingProtocolV1_2`: `tfVaultDepositBlock` is set, and the Vault already has `lsfVaultDepositBlocked`. (`tecNO_PERMISSION`)
9. `LendingProtocolV1_2`: `tfVaultDepositUnblock` is set, and the Vault does not have `lsfVaultDepositBlocked`. (`tecNO_PERMISSION`)

Parent check 2 still applies, so only the Vault Owner can block or unblock deposits.

#### 3.3.4 State Changes

Append to parent [§3.3.3](../README.md#333-state-changes):

4. `LendingProtocolV1_2`: If `tfVaultDepositBlock` is set, set `lsfVaultDepositBlocked` on the `Vault`.
5. `LendingProtocolV1_2`: If `tfVaultDepositUnblock` is set, clear `lsfVaultDepositBlocked` on the `Vault`.

`VaultSet` never changes `lsfVaultOwnerCanBlockDeposit` or `lsfVaultPrivate`.

### 3.4 Transaction: `VaultDeposit`

#### 3.4.1 Failure Conditions

Append to parent [§3.5.2.2](../README.md#3522-protocol-level-failures):

16. - `SingleAssetVault`: The check does not apply.
    - `LendingProtocolV1_2`: The Vault has `lsfVaultDepositBlocked`. (`tecNO_PERMISSION`)

The reference implementation evaluates this check in preclaim after parent check 5 and before parent check 6. The check applies to every depositor, including the Vault Owner.

## 4. Rationale

Deposit blocking is an opt-in Vault capability rather than an unconditional Vault Owner power. The immutable `lsfVaultOwnerCanBlockDeposit` flag records at creation time whether the owner may later pause deposits, so prospective depositors can inspect that authority before they deposit. Existing Vaults cannot acquire the capability.

Blocking an already-blocked Vault, or unblocking an unblocked one, fails instead of succeeding as a no-op. This keeps each successful `VaultSet` with a deposit-blocking flag a real state change.

## 5. Security Considerations

A Vault Owner with `lsfVaultOwnerCanBlockDeposit` can stop and resume deposits at any time. Clients should show both that immutable capability and the current `lsfVaultDepositBlocked` state. Blocking does not affect `VaultWithdraw` or `VaultClawback`, so it cannot by itself stop existing shareholders from redeeming their shares.
