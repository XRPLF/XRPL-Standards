# 65.1.3 Single Asset Vault Cash-Basis Accounting

## 1. Abstract

Under the `LendingProtocolV1_1` amendment, a Single Asset Vault accounts for the interest earned by its Loans on a cash basis. `AssetsTotal` counts interest only once a Borrower has paid it, rather than counting the interest a Loan is expected to earn from the moment the Loan is issued. The share exchange rate of the Vault therefore tracks the assets the Vault holds instead of the income it is owed, and a Borrower who stops paying costs the Vault only the principal it lent out. A Vault created before the amendment keeps instant interest recognition, in which `LoanSet` immediately adds all expected net `InterestDue` to `AssetsTotal` at origination (XLS-66 §3.8.6), because changing the accounting model of an existing Vault would change the value of the shares it has already issued. Which model a Vault uses is recorded in its `LEVersion` field and fixed when the Vault is created.

The Lending Protocol side of the change, which updates `LoanSet`, `LoanPay` and `LoanManage`, is specified in [XLS-66.1.1](../../XLS-0066-lending-protocol/66.1/66.1.1-loan-cash-basis.md).

## 2. Motivation

Instant interest recognition credits a Vault with interest that a Borrower has not paid yet, so the share exchange rate reflects income the Vault has not received. A depositor can redeem shares at a rate inflated by interest that later defaults, and the loss falls on the depositors who remain. Cash-basis accounting removes that mismatch by recognising interest only when it is paid.

Existing Vaults cannot switch accounting models without changing the value of shares already issued, so the model has to be recorded per Vault rather than derived from the amendment state at the time of the transaction.

## 3. Specification

This patch changes the parent [XLS-65](../README.md) sections named below. All other parent behavior is unchanged.

### 3.1 Ledger Entry: `Vault`

#### 3.1.1 Fields

Add this field to parent [§3.1.2](../README.md#312-fields):

| Field Name  | Constant | Required | JSON Type | Internal Type | Default Value | Description                                                                                                                           |
| ----------- | :------: | :------: | :-------: | :-----------: | :-----------: | ------------------------------------------------------------------------------------------------------------------------------------- |
| `LEVersion` |   Yes    |    No    | `number`  |    `UINT8`    | absent (`0`)  | The accounting model the Vault applies to `AssetsTotal`. Absent is treated as `0` (instant interest recognition). Immutable once set. |

For a Vault with `LEVersion == 1`, the parent `AssetsMaximum` field caps deposits only. Collected interest may raise `AssetsTotal` above it.

#### 3.1.2 `LEVersion`

`LEVersion` is a ledger entry schema version. A dedicated version field is used instead of ledger entry flags, because flags allow mutually exclusive variants to be set at the same time. `Vault` is the first ledger entry to use it.

`LEVersion` is set only by the protocol. It is not a field of any transaction and cannot be set or changed by the submitter. `VaultCreate` writes it once, when the Vault is created.

`LEVersion` selects the accounting model of the Vault:

- `LEVersion` absent (treated as `0`, instant interest recognition): `AssetsTotal` includes the full expected net `InterestDue` booked at origination. This is the parent behaviour and continues to apply to every Vault created before the amendment was enabled.
- `LEVersion = 1` (cash basis): `AssetsTotal` excludes uncollected interest and increases only as interest is collected in cash.

A Vault created while the amendment is enabled is always cash-basis; the model is not selectable at creation. A Vault created before the amendment always uses instant interest recognition. Neither can be converted to the other. A later revision of the `Vault` ledger entry would use `LEVersion = 2`.

#### 3.1.3 Exchange Rate

The exchange rate algorithms in parent [§3.1.7.2](../README.md#3172-exchange-rate-algorithms) are unchanged. They operate on `Vault.AssetsTotal` without regard to how interest is recognised into that value. Recognition is defined by the connected protocol; for the Lending Protocol see [XLS-66.1.1](../../XLS-0066-lending-protocol/66.1/66.1.1-loan-cash-basis.md).

#### 3.1.4 Invariants

Immutability of `LEVersion` is specified in [65.1.1 Unmodifiable Vault Fields](./65.1.1-unmodifiable-vault-fields.md) and in parent [§3.1.10](../README.md#3110-invariants) item 14. No invariant checks the value of `LEVersion`; that it is absent or `1` follows from `VaultCreate`.

Parent [§3.1.10](../README.md#3110-invariants) item 11 states that the two `LoanSet` cap checks apply unchanged by either amendment. Replace that statement with:

11. There is no invariant requiring `Vault.AssetsTotal <= Vault.AssetsMaximum` to hold on every modification of the entry, because `Vault.AssetsTotal` grows with interest and interest is not a deposit. The cap is instead enforced per transaction, by the checks in items 12 and 13 and by `LoanSet` (see the [Lending Protocol](../../XLS-0066-lending-protocol/README.md) §3.8.5.2 checks 6 and 14):
    - `LendingProtocol (parent)`: `LoanSet` fails when `Vault.AssetsMaximum` is non-zero and either `Vault.AssetsTotal >= Vault.AssetsMaximum` or `Vault.AssetsTotal + InterestDue > Vault.AssetsMaximum`.
    - `LendingProtocolV1_1`: If `Vault.LEVersion == 1`, those two `LoanSet` checks do not apply, and collected interest may raise `AssetsTotal` above the cap. For a Vault with `LEVersion` absent they apply as above.

A cap already exceeded by collected interest does not block a `VaultSet` that leaves the cap unchanged only under `fixCleanup3_4_0` (parent item 13). This patch does not change that rule.

#### 3.3.1 Response Fields

Add this field to parent [§3.9.2](../README.md#392-response-fields):

## 4. Rationale

The alternative to a per-entry version field is to derive the accounting model from the amendment state at the time each Loan transaction executes. That was rejected because it would silently change the share exchange rate of every existing Vault on the ledger at the moment the amendment activates.

`LEVersion` is a version number rather than a boolean flag so that a later accounting change can be expressed as a further version without another field. The name matches the existing `sfLEVersion` field; `Version` is already used by `AccountRoot`.

## 5. Security Considerations

Cash-basis accounting reduces, but does not remove, the exposure of a depositor to an unpaid Loan: the Vault still carries the principal at face value until the Loan defaults or is impaired. `LossUnrealized` remains the mechanism for reporting an expected shortfall.

Because `LEVersion` is immutable, an implementation must read it from the `Vault` ledger entry rather than from the amendment state when computing the interest accounting of a Loan. Reading the amendment state instead would apply cash-basis rules to Vaults that use instant interest recognition and misprice their shares.
