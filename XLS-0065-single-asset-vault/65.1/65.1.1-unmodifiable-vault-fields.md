# 65.1.1 Unmodifiable Vault Fields

## 1. Abstract

Under the `LendingProtocolV1_1` amendment, `Sequence`, `OwnerNode`, `Owner`, `WithdrawalPolicy`, `Scale` and `LEVersion` are immutable on a `Vault` once set, in addition to `Asset`, `Account` and `ShareMPTID`. The same amendment introduces `VaultKind`, `SubscriptionDate` and `RedemptionDate` through the closed-ended vault proposal, and those three fields are immutable under the same rule. The later `LendingProtocolV1_2` amendment introduces `EarlyExitFeeRate` through the early-exit fee proposal, which joins the set on the same terms.

## 2. Motivation

The version field determines how the Vault values its shares. Changing `LEVersion` after creation would reprice every share in issue.

The identity and configuration fields are in the same position. `Sequence` and `OwnerNode` locate the entry and its directory page, `Owner` names the account that controls it, and `WithdrawalPolicy` and `Scale` fix how shares are redeemed and how finely the asset is denominated. None of them has a legitimate reason to change after creation.

Stating this as a ledger invariant means it holds for every transaction that touches the entry.

## 3. Specification

### 3.1 Ledger Entry: `Vault`

#### 3.1.1 Invariants

Before the amendment:

1. `Vault.Asset == Vault'.Asset`
2. `Vault.Account == Vault'.Account`
3. `Vault.ShareMPTID == Vault'.ShareMPTID`

When the amendment is enabled:

1. `Vault.Sequence == Vault'.Sequence`
2. `Vault.OwnerNode == Vault'.OwnerNode`
3. `Vault.Owner == Vault'.Owner`
4. `Vault.WithdrawalPolicy == Vault'.WithdrawalPolicy`
5. `Vault.Scale == Vault'.Scale`
6. `Vault.Asset == Vault'.Asset`
7. `Vault.Account == Vault'.Account`
8. `Vault.ShareMPTID == Vault'.ShareMPTID`
9. If `Vault.LEVersion` is present, `Vault.LEVersion == Vault'.LEVersion`; if it is absent, it remains absent, except when the transaction creates the entry.
10. If `Vault.VaultKind` is present, `Vault.VaultKind == Vault'.VaultKind`; if it is absent, it remains absent, except when the transaction creates the entry.
11. If `Vault.SubscriptionDate` is present, `Vault.SubscriptionDate == Vault'.SubscriptionDate`; if it is absent, it remains absent, except when the transaction creates the entry.
12. If `Vault.RedemptionDate` is present, `Vault.RedemptionDate == Vault'.RedemptionDate`; if it is absent, it remains absent, except when the transaction creates the entry.

When `LendingProtocolV1_2` is also enabled, the set gains one further field, introduced by the [early-exit fee proposal](../../XLS-draft-early-exit-fee/README.md):

13. If `Vault.EarlyExitFeeRate` is present, `Vault.EarlyExitFeeRate == Vault'.EarlyExitFeeRate`; if it is absent, it remains absent, except when the transaction creates the entry.

## 4. Rationale

Treating these fields as immutable rather than mutable-with-conditions avoids introducing transaction-specific exceptions into a ledger-wide invariant.

## 5. Security Considerations

The invariant is what allows a reader to cache the version and denomination of a Vault. Without it, every consumer would have to re-read the entry before valuing shares.

A field added to the `Vault` later is mutable unless it is included in this set. `VaultKind`, `SubscriptionDate` and `RedemptionDate` are included, so the closed-ended vault's phase schedule cannot be changed after creation. `EarlyExitFeeRate` is included on the same grounds, so the price of an early exit cannot be changed after depositors have committed capital.
